# 프로그램 신청 구조 재정리 결정 기록

작성일: 2026-09-29. 운영 적용 기록: 2026-09-30. 이 문서는 설계 결정과 전환 검증 기록이다.

현재 상태: 운영 DB의 기존 프로그램 43건에 질문 ID를 보존한 공통 신청 양식을 적용했고, 신청·설정 경계와 Firebase Hosting을 배포했다. 버전 검사가 없는 구 신청 RPC·대체 관계의 클라이언트 권한은 회수했다. 신청·회원·알림 원본과 취소 이력은 삭제하지 않았다.

## 전환 전 확인된 상태

- 운영 읽기 전용 집계: 모집형 일반 프로그램 38건, 모집형 챌린지 3건, 프로그램의 구형 추가 질문 1건, 전체 신청 420건, 회차 신청 36건. 개인 정보와 답변 값은 출력하지 않았다.
- 38개 일반 프로그램은 모두 `application_form`이 없었다. 구형 질문이 있던 프로그램의 새 비회원 테스트 신청은 답변은 저장됐지만 당시 질문 사본은 없었다. 테스트 신청은 취소 상태로 보존했다.
- 공개 비회원 화면은 전환 플래그가 켜지면 챌린지까지 `register_guest_program_application`으로 보낸다. 이 함수가 호출하는 `program_application_transition`은 챌린지를 거부한다. 현행 회귀 검사는 이 조합을 포함하지 않았다.
- 설정 화면은 일반 프로그램에 `application_form`, 챌린지에 `guest_properties.custom_fields`를 사용한다. 프로그램 종류를 바꾸면 질문의 기준이 달라질 수 있다.
- 관리자 명단의 챌린지 제거는 일반 프로그램과 달리 응답 행을 삭제한다. 새 구조에서 취소를 상태로 보존하려면 관리자 취소도 같은 전이로 옮겨야 한다. 챌린지 참가 수·커뮤니티 접근은 `JOIN` 상태를 확인하므로 취소 상태 행을 참가자로 세지 않는다.
- 새 `application_form` 필수 제약을 먼저 적용하면 현재 관리자 생성 화면의 빈 양식 저장이 실패한다. 관리자 화면이 모든 프로그램에 정규 양식을 저장하도록 준비한 뒤 제약을 적용해야 한다.
- `WriteForm`은 공지 저장 후 프로그램 설문과 챌린지 미션을 별도 요청으로 저장한다. 후속 요청 실패 시 설정 저장의 원자성이 없다. 이 문제는 질문 이관과 분리해 영향 검증 후 고쳐야 한다.

## 최종 구조 원칙

1. **질문 정의는 하나**: 모집형 일반 프로그램, 회차 프로그램, 챌린지 모두 `notices.application_form`을 사용한다. 대상(`MEMBER`, `GUEST`, `ALL`)은 질문별 속성이다. `guest_properties.custom_fields`는 원본 보존용 구형 데이터로만 남기고 새 화면·신청·검증에서 읽거나 쓰지 않는다. 별도 질문 버전 테이블은 만들지 않는다.
2. **버전은 동시성 검사에만 사용**: 질문 정의가 실질적으로 바뀔 때 `application_form_revision`을 증가시킨다. 신청 화면이 보여준 revision을 제출하고 DB가 잠금 안에서 최신 revision과 비교한다. 일치하지 않으면 신청과 비회원 계정 갱신을 모두 거부하고 새 질문을 다시 보여준다.
3. **응답마다 당시 정의를 보존**: 전체·회차 신청은 상태, 답변, revision, form snapshot을 한 트랜잭션에서 기록한다. 취소·재신청 이력도 기존처럼 보존한다. 과거 응답에 없던 snapshot은 추측해서 채우지 않는다.
4. **쓰기 경계는 신청 단위로 명확히**: 회원 전체/챌린지 신청은 동일한 검증·정원·취소 전이를 사용하고 유형별 운영 규칙만 분리한다. 회차는 별도 회차 전이를 사용하되 질문 검증·버전 규칙은 공유한다. 비회원 신원 처리와 신청은 한 DB 트랜잭션이다. RPC와 필수 직접 관계 대체 경로는 같은 DB 함수를 호출한다.
   비회원은 연락처 잠금 → 회차(해당 시) → 프로그램 잠금 순서를 구·신 경로에서 동일하게 유지해 전환 중 교착을 피한다. 관리자 챌린지 취소도 행 삭제 대신 보존형 취소·대기 승급을 사용한다.
5. **구형 브라우저는 실패를 명확히**: 새 경로 검증 후 일반·챌린지의 구형 직접 신청 쓰기와 버전 검사가 없는 RPC·관계 쓰기 권한을 회수한다. 내부 새 함수는 동일한 DB 구현을 재사용하되 구형 브라우저에는 새로고침을 요구한다. 재전송이나 임의의 구형 경로 복귀로 답변·정원·이력이 달라지지 않게 한다.
6. **설정 저장은 도메인 단위로**: 공지 본문, 신청 질문, 설문 연결, 챌린지 미션 중 같은 저장 버튼으로 확정하는 데이터는 하나의 저장 경계로 묶거나 실패 시 명확히 분리된 저장 단계로 표시한다. 부분 성공을 전체 성공으로 알리지 않는다. UI는 작은 영역 컴포넌트로 유지하되 데이터 조립·검증은 공통 도메인 모듈에 둔다.

## 변경 순서와 중단 조건

1. 현행 경로별 회귀 시험을 만든다. 일반/챌린지/회차 × 회원/비회원 × 질문 유무 × 신청/취소/재신청, 정원 경합, 관리자 현장 추가, 알림 실패, 질문 편집 중 신청을 포함한다. 기존 실패도 기록해 원인을 분리한다.
2. 모든 프로그램의 구형 질문을 질문 ID 그대로 단일 정의로 이관하는 검토용 마이그레이션을 만든다. 운영 집계·DB 트리거·후속 테이블 영향과 복구 경로를 확인하고 트랜잭션 롤백 시험을 통과해야 한다. 응답·로그는 수정하지 않는다.
3. 관리자 양식 저장을 먼저 정규화해 신규·기존 일반/회차/챌린지가 모두 빈 양식을 포함한 단일 정의를 저장하게 한다. 그다음 DB 전이와 공개/회원 UI를 함께 전환하고 격리 PostgreSQL에서 기능·권한·병렬성·실패 원자성을 검증한다. 검증되지 않은 챌린지 경로를 단순 프런트 분기로 우회하지 않는다.
4. 운영 스키마는 리뷰된 마이그레이션과 영향 점검, 사용자 승인 뒤에만 적용한다. Firebase Hosting 배포도 명시된 배포 지시 범위에서만 수행한다. 각 단계 후 객체/건수/권한/오류를 확인하고, 불일치 시 다음 단계로 가지 않는다.
5. 배포 후 알림은 요청대로 Slack/LINE을 일시적으로 끄고 합성 신청을 시험하되, 기존 설정을 정확히 복원한다. 생성된 신청/로그는 삭제하지 않고 테스트 신청만 취소 상태로 남긴다.

## 완료 조건

- 모든 유형의 신규 신청에 당시 질문 snapshot과 revision이 있다.
- 질문 편집과 경합한 신청은 계정·응답의 부분 쓰기 없이 거부된다.
- 기존 프로그램·질문 ID·현재 명단·취소 이력·출석·설문·포인트·커뮤니티 자격·알림 설정이 유지된다.
- 관리자 설정 저장과 공개/회원 신청의 실제 경로 및 오류 메시지를 확인하고 회귀 검사와 빌드가 통과한다.
- 남은 구형 경로와 기능 플래그를 제거하거나, 제거 불가 이유와 종료 조건을 문서화한다.

- 전환 플래그는 기본 활성이다. `false`는 아직 이관하지 않은 독립 개발 DB에만 남겨 둔 임시 호환 모드이며 운영 DB에서는 구 RPC 권한이 없어 사용할 수 없다. 다음 별도 정리에서 이 모드와 도달 불가능한 구 클라이언트 코드를 제거할 수 있다. 공개 전환에는 필요하지 않고 무리한 동시 삭제로 회귀 위험을 늘리지 않기 위해 이번 배포에는 포함하지 않았다.

## 2026-09-30 최종 클라이언트 정리와 실사용 확인

- 운영에서 사용할 수 없는 전환 플래그와 구 클라이언트 신청/설정 저장 분기를 제거했다. 모든 프로그램 종류는 공통 질문 정의와 버전 검사 신청 경계를 사용한다. 구 DB 함수는 새 원자적 함수의 내부 구현에서 계속 참조될 수 있으므로 운영 스키마를 추가로 삭제하지 않았다. 환경 예시와 Firebase 배포 워크플로의 전환 플래그도 제거했다.
- 클라이언트 경계 검사를 현재 단일 경로에 맞춰 강화했고, 기준선 31/31, 배포 빌드, 계정 보안 사전 검사를 통과한 뒤 Firebase Hosting `sci-center-6f265`에 다시 배포했다. `npm run dev`로 로컬 서버를 실행해 `/`, `/admin`, `/p/150`의 HTTP 200도 확인했다(로컬 브라우저 렌더링 검증은 별개). 운영 DB 롤백 시험은 관리자 저장, 동시 수정 충돌, 직접 관계 대체 경로, 일반/챌린지/반복 회차의 회원·비회원 신청과 질문 사본, 정원·대기 승급, 설문 저장을 재확인했다. 합성 시험 데이터는 모두 롤백했다.
- 실제 관리자 화면에서 비공개 시험 프로그램(ID 150)을 만들고 회원 필수 질문과 비회원 필수 질문을 각각 설정해 저장했다. 목록 표시와 다시 연 설정 화면에서 두 질문의 대상·필수 여부가 유지됨을 확인했다. 프로그램은 신청 0건·푸시 예약 0건을 확인한 뒤 `CANCELLED`로 전환했고 기록을 보존했다.
- 시험 전 프로그램 알림 네 경로를 점검해 하이픈 Slack만 켜져 있음을 확인했다. 이를 일시적으로 끈 후 실제 DB 값이 모두 꺼졌음을 재조회했다. 비회원 브라우저 신청은 관리자 세션 리디렉션과 브라우저 확인 창 제어 장애로 제출하지 못했다. 하이픈 Slack을 원래 ON으로 복원하고, 다른 세 프로그램 경로는 원래 OFF임을 DB에서 다시 확인했다. 신청 알림은 발생하지 않았고 시험 프로그램의 신청도 0건이다.
- 따라서 **관리자 화면 저장의 실사용 검증은 완료**, **브라우저에서의 비회원/회원 최종 신청 제출 검증은 미완료**다. 이 부분을 완료로 표현하지 않는다. 기능 경계는 격리 DB 회귀 검사와 운영 DB 롤백 시험에서 확인했지만, 실제 브라우저 제출 성공·오류 메시지까지 보증하는 것과는 다르다. 로컬 브라우저 접속은 환경 보안 정책상 차단되어 시도하지 않았다.

## 2026-09-30 비회원 실제 제출 추가 검증

- 관리자 세션과 분리된 공식 Firebase Hosting 보조 도메인에서 비공개 시험 프로그램 ID 150의 비회원 신청을 실제 제출했다. 비회원 전용 필수 질문이 표시되고, 합성 신청 정보로 성공 화면까지 도달했다. 운영 DB에서 신청 1건의 `JOIN`, revision 1, 신청 당시 양식 사본과 비회원 답변 저장을 확인했다. 관리자 명단에서도 같은 질문·답변이 보였다.
