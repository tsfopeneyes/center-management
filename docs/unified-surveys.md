# 통합 설문 구현 및 운영 적용 검토

입실·퇴실·프로그램·공유 링크에서 같은 질문 편집기와 결과 화면을 사용하는 통합 설문 기능을 구현했다. 운영 DB에는 기존 데이터를 삭제하거나 이동하지 않는 추가 마이그레이션으로 적용한다.

## 구현 범위

- 설문 관리: 생성, 복제, 보관, 기존 설문 가져오기, 응답 조회, 독립 설문 링크 공유.
- 문항: 단답형, 장문형, 단일 선택, 복수 선택, 5점 별점. 문항 추가·삭제·복제·순서 변경·필수 여부·대표 만족도·추가 의견·선택지별 콘텐츠 추천을 설정한다.
- 연결: 설문 목록에서 센터별 입실·퇴실만 바로 선택한다. 입퇴실은 일반 설문 하나와 선택적인 기본 설문 하나를 둘 수 있으며 한 번에 하나만 노출한다. 프로그램 설문은 프로그램을 만들거나 수정할 때만 설정한다.
- 응답 정책: 연결별 1회 또는 방문마다. 프로그램은 신청/출석 대상, 종료 후/기간 중 작성, 시작·마감 설정. 프로그램 응답은 기간 내 수정 가능. 입퇴실 응답은 확정 후 수정하지 않는다.
- 버전: 배포된 문항은 불변이다. 설문을 수정하면 새 버전을 만들고 그 설문의 현재 연결을 새 버전으로 갱신한다. 기존 응답의 질문 스냅샷은 바뀌지 않는다. 열어 둔 설문 버전이 변경되면 제출을 거부하고 다시 열도록 한다.
- 비교: 동일 설문의 같은 문항 ID·문구·유형·선택지·지표에 한해 프로그램별 평균/선택지 비율/의견을 비교한다. 미응답과 집계 제외 응답은 평균에서 제외한다. 복수 선택 비율의 분모는 해당 문항 응답 수다.
- 응답 경로: 학생 입실·퇴실, 키오스크, 게스트 QR 입실·퇴실, 프로그램 피드백, 로그인 사용자의 공유 링크. 기존 입퇴실 기록과 알림 흐름을 사용한다. 선택 설문 조회 장애가 키오스크 입퇴실을 막지 않게 처리했다.
- 템플릿: 템플릿 자체는 응답을 받거나 입퇴실·프로그램·공유 링크에 연결되지 않는다. 프로그램에서 템플릿을 선택하면 질문을 복사하여 그 프로그램 소유의 새 설문을 만든다. 같은 템플릿을 쓴 프로그램 결과는 템플릿 결과 화면에서 비교할 수 있지만 원본 응답은 각 프로그램 설문에 저장한다.
- 프로그램 포인트: 새 응답과 보상을 같은 트랜잭션에서 저장한다. 프로그램·회원 잠금 및 기존 지급 내역 확인으로 새 설문 경로의 중복 지급을 막는다. 답변 수정은 보상을 다시 지급하지 않는다.
- 계정 병합: 새 응답도 게스트→회원 이동 대상에 포함한다. 중복 응답은 원본을 보존하고 별도 응답 키 및 집계 제외로 남긴다. 예상치 못한 충돌 때 원본을 삭제하지 않고 병합을 중단한다.

## 데이터 구조

| 테이블 | 역할 |
|---|---|
| `survey_forms` | 설문의 독립 정체성·보관 상태 |
| `survey_versions` | 불변 질문 정의 |
| `survey_links` | 버전과 센터/프로그램의 연결·노출 정책 |
| `survey_entries` | 응답·당시 질문·연결·응답자·방문 식별자 |
| `survey_completions` (뷰) | 입퇴실 1회 정책 확인용 완료 여부. 답변 본문을 노출하지 않음 |

공유 링크는 `survey_links`의 `PUBLIC` 연결과 공개 토큰을 사용하며 로그인한 이용자에게 1회만 응답을 허용한다. `notices.guest_properties.survey_version_id`와 프로그램 연결은 트리거로 동기화한다. 게시물 저장과 연결 변경은 같은 트랜잭션 안에서 처리된다. 프로그램 저장 RPC가 없을 때는 동일한 직접 테이블 저장 절차를 사용한다.

## 기존 데이터 호환

원본 `surveys`, `survey_assignments`, `checkin_surveys`, `program_feedback`, `visit_notes`를 일괄 이동하거나 삭제하지 않는다. 통합 연결이 없는 대상은 기존 로직을 유지한다. 통합 연결을 해제한 대상에서 오래된 설문이 다시 살아나지 않도록 해제 이력을 남긴다. 프로그램 편집에서 명시적으로 기존 피드백을 다시 선택하면 그 선택을 따른다.

기존 설문을 가져오면 최초 버전의 `legacySource`로 원본 출처를 기록하고 결과 화면에서 과거 응답을 함께 조회한다. 복제 설문은 과거 응답 출처를 복제하지 않는다. 과거 퇴실 `visit_notes` 변환 내역은 기존 설문 결과 화면에서 계속 조회할 수 있다. 원본 질문 스냅샷이 없는 과거 프로그램 응답은 현재 설정을 참고해 표시하되 비교에서 제외한다. 복원 불가능한 과거 질문을 확정된 사실처럼 표시하지 않는다.

기존 맞춤 피드백에 저장된 가짜 기본 만족도 5점은 조회 정규화 과정에서 제외한다. 새 응답에는 이 고정 칸을 사용하지 않는다. 프로그램별 피드백 조회·통계·학생 작성 여부·회원 상세 조회는 공통 읽기 API를 사용한다.

## 권한과 검증

- 관리 작업은 기존 `is_current_staff()`를 사용한다. 회원은 자기 응답만 읽는다. 프로그램 응답은 로그인 및 참가 조건을 확인한다.
- 게스트 입퇴실은 기존 공개 방문 접수 경로에 맞춰 최근 방문 확인 후 저장한다. 방문 ID는 기존 시스템에서 공개될 수 있으므로 강한 본인 인증 수단으로 취급하지 않는다. 비로그인 사용자에게 새 응답 본문 조회 권한은 부여하지 않는다. 완료 여부만 제한적으로 확인한다. 프로그램 응답은 이 게스트 경로를 사용하지 않는다.
- DB가 링크 활성 상태·기간·출석·실제 방문·센터 일치·문항·답변 타입·옵션·필수 답변·스냅샷·중복을 검증한다.
- 직원의 집계 제외 변경은 답변 수정과 분리한다. 새 설문과 응답에 삭제 권한을 부여하지 않는다.

2026-09-10 읽기 전용 검토에서 실제 운영 스키마의 `notices.id`/`logs.id`는 bigint, `locations.id`는 text, `users.id`는 uuid임을 확인하여 반영했다. 새 테이블 이름 충돌은 없었고 필요한 권한 함수 두 개는 존재했다. 기존 연결 계정에는 원본 테이블 행 수 조회 권한이 없으므로 운영 응답 수 대조는 미완료다. 관리자 역할 전환 재시도는 자동 승인 검토에서 거부되었으며, 이후 역할 전환 없이 허용된 메타데이터만 조회했다.

## 재현 가능한 로컬 검증

- `npm run test:surveys`: 메모리 PostgreSQL(PGlite)에서 실제 스키마 형식으로 마이그레이션 실행, 원본 보존, 권한·응답·버전·보상·병합 검증. 운영 DB에 연결하지 않는다.
- `node scripts/test-account-merge-service.mjs`
- `node scripts/test-account-merge-safety.mjs`
- `npm run build`
- 실행 중인 Vite의 `http://localhost:5173/scripts/fixtures/survey-ui.html`: 메모리 예시 데이터만 사용하는 편집·연결·비교·응답 UI 검증 페이지. 운영 테이블에는 쓰지 않으며 정식 빌드 진입점에도 포함하지 않는다.

브라우저에서 질문 수정→B 프로그램만 새 버전 적용(A 유지), 프로그램별 4점/5점 비교, 선택지 비율, 필수 문항 오류, 모든 질문 유형 제출을 확인했다. 휴대폰 크기에서도 응답 화면을 확인했다. 이 검증은 UI 예시 데이터와 로컬 DB 검증을 조합한 것으로, 운영 DB까지 연결한 전체 시나리오 검증은 아니다.

최종 로컬 DB 검증은 26개 안전·동작 확인과 문항/비교 모델 검증을 통과했고, 기존 계정 병합 서비스·클라이언트 안전 테스트도 통과했다. 과거 프로그램 피드백이 있는 사람에게는 프로그램 이름이 바뀌어도 새 설문 보상을 다시 지급하지 않는다. 과거 지급 실패 여부의 복구는 기존 지급 내역을 확인한 후 별도로 처리한다.

## 운영 적용 순서

1. 검토 대상 SQL: `supabase/manual/proposals/20260910_unified_surveys.sql`. 아직 정규 마이그레이션 폴더에 넣지 않아 자동 적용되지 않는다.
2. 권한 있는 담당자가 기존 설문·응답·로그·포인트 행 수를 기록하고 복구 가능한 백업을 확인한다. SQL과 계정 병합 변경을 검토하고 명시적으로 승인한다.
3. SQL을 한 트랜잭션으로 적용한다. 기존 설문 데이터의 백필·삭제·리셋은 없다. 적용 전후 기존 행 수를 대조한다.
4. 변경한 계정 병합 서비스도 운영 인증 서비스에 반영한 뒤 게스트 응답을 수집한다. 서비스 반영 전에는 안전 장치가 새로운 응답을 가진 게스트의 병합을 중단할 수 있다.
5. 로컬 앱을 승인된 DB에 연결해 직원·회원·키오스크·게스트 각각 생성/연결/제출/수정/권한 거부/보상을 확인한다. 이 단계에서 실제 알림·포인트가 발생할 수 있으므로 별도 시험 계정을 사용한다.
6. 기존 설문을 가져와 필요한 연결부터 단계적으로 전환한다. 기존 응답은 계속 원본에서 조회한다.
7. Firebase Hosting 배포는 사용자의 별도 명시적 지시 후 진행한다.

복구는 새 수집을 중단하고 이전 앱과 저장해 둔 기존 프로그램 설정을 복원하는 방식으로 한다. 새 테이블·응답을 삭제하여 되돌리지 않는다. 운영에서 수집된 원본은 복구 과정에서도 보존한다.
