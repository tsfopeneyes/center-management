### 취소·재신청 이력 보존 설계 갱신 (2026-09-29)

- 전체 프로그램 신청은 기존 `notice_responses` 행을 지우지 않고 `CANCELLED`와 `cancelled_at`으로 보존한다. 취소 시 기존 답변·질문 스냅샷·출석값은 그대로 둔다. 재신청으로 같은 `(notice_id, user_id)` 행을 재사용하기 직전에 이전 취소 신청 전체를 접근 제한된 `program_application_attempt_history`에 보존한다. 회원 화면과 관리자 현재 명단은 취소 행을 활성 신청으로 취급하지 않는다.
- 회차 신청은 이미 취소 행을 보존하지만, 재신청 시 답변이 덮이는 문제를 막기 위해 별도 비공개 시도 이력 테이블과 보존 트리거를 추가하는 초안을 마련했다. 기존 취소 알림을 잃지 않도록 전체 신청의 `DELETE` 알림은 유지하면서 새 `UPDATE → CANCELLED`에도 한 번만 알리는 안을 검증 중이다.
- 관리자 명단의 일반 프로그램 ‘삭제’도 새 전환에서는 별도의 권한 확인·잠금·대기 승급이 있는 기록 보존형 취소로 연결한다. 신청자 본인과 달리 모집 마감 후 명단 정정이 가능해야 한다. RPC 캐시가 늦을 때에는 동일한 DB 함수를 부르는 INSERT 전용 관계로 대체한다. 챌린지와 전환 전 클라이언트의 기존 동작은 유지한다.
- 세 SQL(`20260929_program_application_cancellation_history.sql`, `20260929_program_application_transition.sql`, `20260929_session_application_attempt_history.sql`)은 **운영 미적용**이다. 격리 DB 검사에서 취소·중복 취소·재신청·답변 보존·비공개 이력 권한·대기 승급이 통과했고, 25/25 기준선과 빌드도 통과했다. 이는 운영 Auth/RLS/트리거와 배포된 클라이언트의 전체 동작 보증은 아니다.
- 남은 전환 전 확인은 운영과 동일한 트리거·정책의 충돌, 실제 배포된 클라이언트와 Auth/API의 통합 동작이다. 클라이언트 전환과 직접 쓰기 차단은 동시 롤아웃이 필요하므로 Firebase 배포 지시 없이 운영 전환 SQL만 적용하지 않는다.
- 보존안 수정 후 실제 로컬 PostgreSQL 17에서 전체/회차 SQL을 다시 적용하고 각각 정원 1명의 동시 신청·취소·제3자 신청 10회, 동일 연락처 비회원 병렬 등록을 통과했다. 전체 신청은 취소 행 1건을 포함해 세 행이 남고, 기존 대기자가 승급한다. 격리 기준선도 25/25 통과했다. 이 검사는 운영 프로젝트 자체의 RLS/외부 서비스 설정을 재현하지는 않는다.
- 추가 읽기 전용 운영 대조에서 관리자 판정 함수와 모집 검증 트리거의 관리자 예외가 동일한 권한 기준임을 확인했다. 운영 함수의 기존 회차 이관·커뮤니티 자격·프로그램 설문·종료 보상은 `JOIN`/`WAITLIST`를 명시적으로 사용해 `CANCELLED`를 현재 참가자로 취급하지 않는다. 격리 테스트에는 운영 모집 검증 트리거 조건을 반영하고, 모집 마감 후 관리자 취소 및 대기 승급을 추가해 통과했다. 운영 데이터·권한은 변경하지 않았다.
- 화면 소비자 재점검에서는 출석 여부만으로 수를 세던 프로필·키오스크·관리자 달력·통계가 보존된 취소 행을 잘못 포함할 수 있음을 발견했다. 현행 집계와 CSV 상세 로그는 취소 행을 제외하고, 참석 인원은 `JOIN`이면서 출석한 신청만 세도록 보완했다. 취소 행의 원래 출석값은 DB에 남겨 기록 보존과 현재 인원 계산을 분리한다. 이 규칙을 공통 함수와 회귀 검사에 넣어 기준선 26/26을 통과했다.
- 공개 신청의 결과 전달을 재점검해, 대기 신청에도 외부 알림 요청이 `JOIN` 기본값으로 나가던 문제를 수정했다. 저장된 실제 `JOIN`/`WAITLIST` 상태를 회원·비회원 알림 모두에 전달하고, 비회원 전체 프로그램 신청 직후 화면에도 완료 상태를 즉시 반영한다. 재신청은 새 `created_at`으로 별도 알림 식별자를 가지며, 개발 서버의 실제 외부 알림은 계속 차단한다.
- 관리자 현장 추가는 기존에 취소 신청을 `upsert`할 때 과거 답변을 새 신청에 붙일 수 있고, 다중 추가 중간 실패 시 일부만 반영될 수 있었다. 새 기능 플래그에서만 사용하는 `20260929_staff_program_walkins.sql` 초안을 마련해 전체/회차별 관리자 권한 확인·기록 잠금·일괄 원자 처리를 수행한다. 활성 신청의 답변은 보존하고, 취소자의 이전 답변은 이력 트리거에 보존한 뒤 새 수동 참여의 답변을 비운다. 관리자 회차 취소도 같은 잠금 경계에서 처리해 대기자를 승급한다. RPC 캐시 지연 시 동일 함수로 이어지는 INSERT 전용 관계를 사용한다. 이 SQL과 운영 전환은 아직 미적용이다.
- 위 현장 추가·회차 취소 초안은 PGlite에 이어 임시 로컬 PostgreSQL 17에서도 같은 테스트를 통과했다. 권한 거부, 다중 추가 원자 롤백, 활성 답변 보존, 취소 답변 이력, 중복 취소, 회차 대기 승급을 확인했다. 테스트 서버·임시 DB·포터블 도구는 포트 종료 확인 후 삭제했으며 운영 DB에는 쓰지 않았다.
- 운영 스키마 읽기 전용 재대조에서 회차의 `capacity`·`voided_at`, 두 신청 테이블의 생성 시각·답변·질문 스냅샷 열, 기존 회차 취소 시각·상태 제약을 확인했다. 새 SQL이 요구하는 전체 신청 `cancelled_at`은 **아직 운영에 없는 열**이며, 앞선 취소 이력 마이그레이션과 함께 적용해야 한다.

`notice_responses`는 최소 16개 화면·훅·API 파일에서, `daily_program_session_responses`는 최소 7개 파일에서 직접 참조된다. 이는 정적 문자열 검색으로 확인한 **최소치**이며 DB 함수·트리거와 동적 호출은 별도로 조사해야 한다. 기존 GitHub Actions는 빌드를 실행하지만 이 회귀 묶음은 아직 자동 실행하지 않는다. 인증된 화면의 전후 스크린샷/동작 비교, 운영 스키마·RLS 실상, 직접 테이블 대체 경로의 경쟁 조건 검증이 다음 변경 전 공백이다.

특히 `programSessionsApi.respond()`의 회원 직접 테이블 대체 경로는 현재 클라이언트가 `join_count`로 참여/대기를 계산하고, 취소 후 대기자 승급도 별도 요청으로 수행한다. 저장소의 회차 신청 RLS/트리거만으로 RPC와 같은 원자성이 보장되는지는 확인되지 않았다. 운영 DB가 저장소와 다를 수 있으므로 이를 즉시 운영 장애라고 단정하지 않되, **회원 질문이나 신청 저장 경로 변경 전** 격리 DB 동시성 검사와 운영 스키마 읽기 전용 점검을 필수로 한다. 직접 테이블 경로도 동일한 DB 검증·잠금·권한을 거치게 하는 것이 전환 조건이다.

`node scripts/audit-member-session-fallback.mjs`는 저장소의 회차·게스트·반복 프로그램 마이그레이션만 적용한 PGlite에서 회원 2명의 RPC 신청(`JOIN`, `WAITLIST`) 이후 제3회원의 직접 테이블 `JOIN` 삽입을 시도한다. 2026-09-29 결과는 **정원 1명에 `JOIN` 2명**으로, 안전성 검사 실패(종료 코드 1)다. 이 스크립트는 의도적으로 `test:baseline`에 넣지 않은 미해결 위험 검사이며, 운영 DB에 연결하지 않는다. 운영 DB의 실제 정책·트리거가 같다는 뜻은 아니다. 새 신청 구조의 직접 테이블 경로를 설계할 때 이 검사를 통과 조건으로 사용하고, 이후 취소/승급 동시성·권한·질문 검증 사례를 확장한다.

`scripts/audit-live-program-application-schema.mjs`로 연결된 운영 DB의 관련 컬럼·RLS 정책·트리거·함수 **정의만** 읽기 전용 트랜잭션에서 확인했다(신청자 행과 답변은 조회하지 않음). 운영 회차 신청 테이블에는 출석 자동 처리와 `join_count` 갱신 트리거가 있지만, 직접 쓰기의 정원/대기 판정 트리거는 확인되지 않았다. 운영 `respond_to_program_session` RPC는 회차 행을 잠그고 정원을 판정한다. 반면 현재 클라이언트의 직접 테이블 대체 경로는 클라이언트 카운트를 사용한다. 프로그램 전체 신청도 `useNotices`가 정원과 승급을 여러 요청으로 처리하고, 확인한 `notice_responses` 트리거는 모집 시간은 검사하지만 정원은 검사하지 않는다. **운영 데이터에 쓰기 재현은 하지 않았으며**, 실제 초과 기록이 있는지는 조사하지 않았다. 향후 설계에서는 전체/회차 양쪽의 상태 전이를 DB의 단일 원자적 경계로 옮겨야 한다.

### 진행 중인 첫 안전 경계: 회원 회차 신청

- `supabase/manual/proposals/20260929_member_session_write_boundary.sql`은 **검토용 초안이며 운영에 적용하지 않았다**. 기존 회차 신청 RPC의 자격·시간·정원 규칙은 유지하면서 중복 요청의 상태 보존, 취소 후 대기자 승급의 단일 트랜잭션 처리, 회원 직접 응답 테이블 쓰기 차단을 담았다. 관리자용 명단 추가/출석 변경 정책과 게스트 신청 RPC는 유지한다.
- RPC가 스키마 캐시 문제로 보이지 않을 때 `src/api/programSessionsApi.js`는 빈 삽입 전용 PostgREST 뷰를 사용한다. 이 뷰의 트리거가 같은 RPC를 호출하므로 화면에서 정원이나 대기자를 계산하지 않는다. 뷰조차 없으면 안전하지 않은 직접 쓰기를 시도하지 않고 오류를 돌려준다.
- `scripts/test-member-session-write-boundary.mjs`는 격리 DB에서 정원 1명, 대기 순서, 취소 승급, 중복 신청·취소, 다른 회원 사칭 거부, 닫힌 회차 거부, 관리자 직접 출석 작업, 게스트 신청, 기존 답변·출석 보존을 확인했다. `scripts/test-program-settings-jsx-bindings.mjs`는 화면 분리 중 발생하기 쉬운 누락된 컴포넌트·아이콘 참조를 검사한다. 두 검사를 기준선에 추가한 뒤 **16/16 통과**했고, 최신 `npm run build`도 통과했다. 실제 동시 요청은 PGlite 단일 연결 검증만으로 보증할 수 없으므로 운영 적용 전 별도 동시성 검증이 필요하다.
- 적용 순서: 운영 함수·정책 정의 재대조 → 마이그레이션 검토와 명시적 승인 → 롤백 트랜잭션 드라이런/영향 점검 → DB 변경 및 스키마 캐시 확인 → 새 클라이언트 배포(별도 명시적 지시 필요). 구 클라이언트의 위험한 직접 쓰기는 DB 변경 후 거부된다. 비상 복구에서는 신규 뷰·함수와 정책/함수 변경의 정확한 이전 정의를 복원해야 하지만, 옛 회원 직접 쓰기 정책을 되살리면 정원 초과 위험도 돌아오므로 우선 새 RPC/뷰를 복구하는 방향으로 처리한다. 원본 신청 행·답변·출석·로그는 삭제하지 않는다.
- 이것은 회차 신청의 첫 경계만 검증한 것이다. 전체 프로그램 신청(`notice_responses`)의 동시성, 회원 추가 질문의 불변 버전·DB 검증, 전체 신청 기록원 전환은 아직 미완료다. 따라서 전체 기능의 안전을 확인했다고 주장하지 않는다.

### 2026-09-29 신청 기능 추가 점검

- 회원·비회원·공통 질문의 대상, 정의, 필수/선택지/답변 크기를 검사하는 `src/features/programs/applicationFormModel.js`를 독립 모델로 추가했다. 기존 비회원 질문은 원래 ID를 보존하는 변환 함수로만 읽으며, 운영 저장 형식은 바꾸지 않았다. 격리 회귀 검사 17/17과 빌드가 통과했다. 아직 화면/DB에 연결하지 않았으므로 회원 질문이 운영 기능으로 활성화된 것은 아니다.
- 연결된 운영 DB의 **정의만** 읽기 전용 트랜잭션으로 재점검했다. 신청 테이블 두 개 모두 현행 열에 질문 버전 ID가 없고, `notice_responses`에는 넓은 공개 쓰기 정책이 남아 있다. 현재 모집 검사 트리거는 시간과 상태를 확인하지만 정원, 답변, 신청자 본인 여부를 검증하지 않는다. 신청 상태와 프로그램 ID가 동일한 UPDATE는 일찍 반환하므로 출석/계정 병합을 허용하는 대신 답변 변경도 별도로 제한하지 않는다. 운영 신청 행이나 개인정보를 조회하거나 쓰지 않았다.
- `notice_responses`의 취소는 기존 클라이언트에서 행 삭제이며, 상당수 소비자가 응답 행의 존재 자체를 사용한다. 회차처럼 `CANCELLED` 행을 보존하는 방식으로 일괄 변경하면 참가 자격·집계·중복 확인이 바뀔 수 있다. 전체 프로그램은 당장 삭제 의미를 유지하고 원자적 승급을 별도로 설계하거나, 모든 소비자를 함께 전환해야 한다.
- 공개 비회원 전체 프로그램 신청은 게스트 `users` 행을 먼저 만들고 `notice_responses`를 별도 요청으로 삽입한다. 두 번째 요청 실패 시 계정만 남을 수 있고, 클라이언트에 정원 확인을 맡긴다. 회원/비회원 질문을 하나의 안전한 신청 경계로 묶을 때 이 순서와 중복/재시도를 함께 재설계해야 한다.
- 기존 답변에는 질문 당시 정의가 저장되지 않았다. 현재 `guest_properties.custom_fields`를 과거 버전으로 단정해 덮어쓰지 않는다. 이후 불변 버전은 신규 신청부터 정확히 연결하고, 이전 답변은 원본 그대로 유지하며 정의의 역사적 불확실성을 표시해야 한다.
- 기본 CLI 역할(`cli_login_postgres`)에는 `notices`, 두 신청 테이블, `users`, 회차 테이블의 SELECT 권한이 없다. 사용자의 명시적 읽기 권한 요청 후, **영구 GRANT 없이** 프로젝트 식별자·역할 소속을 확인하고 `BEGIN READ ONLY` 안에서 `SET LOCAL ROLE postgres`를 사용해 집계했다. 트랜잭션은 끝에 ROLLBACK한다. 신청 행, 개인정보, 답변 원문은 출력하지 않았고 운영 데이터·권한을 변경하지 않았다.
- 집계 시점의 프로그램 43개 중 기존 비회원 추가 질문이 있는 프로그램은 1개(질문 1개)이며 새 모델의 이전 검사에 걸리는 형식은 0개다. 모집 중인 비챌린지 프로그램 31개는 이전 형식으로 `application_scope`가 비어 있고, 5개는 `PROGRAM`, 2개는 `SESSION`이다. 챌린지는 별도 3개다. 전체 응답은 `JOIN` 419개(비챌린지 386, 챌린지 33)이며 그중 3개는 현재 `SESSION` 범위인 프로그램의 기존 전체 응답이다. 회차 응답은 `JOIN` 31개, `CANCELLED` 5개다. 두 응답 테이블 모두 집계 시점에 비어 있지 않은 `application_answers`는 0개였다. 이 수치는 이 시점의 집계이며 이후 변할 수 있다.
- 운영 제약조건도 대조했다. 두 테이블은 각각 `(notice_id,user_id)`와 `(session_id,user_id)` 중복을 막는다. 전체 응답의 상태 제약은 `JOIN/DECLINE/WAITLIST/UNDECIDED`만 허용하며 `CANCELLED`는 없다. 회차 응답은 `CANCELLED`를 허용한다. 따라서 전체 응답 취소 의미를 회차와 똑같이 바꾸는 것은 기존 동작을 깨뜨린다.
- `supabase/manual/proposals/20260929_application_form_snapshots.sql`은 **운영 미적용·단독 적용 금지** 초안이다. 현재 질문 정의와 revision을 `notices`에, 신청 당시 스냅샷을 기존 두 응답 테이블에 nullable 열로 추가하는 확장안이다. 격리 DB에서 과거 행·답변 보존, 같은 정의 재저장 시 revision 유지, 정의 변경 시 증가, 잘못된 유형·선택지·중복 ID 거부를 확인했다. 아직 신청 RPC/직접 대체 경로가 스냅샷과 답변을 원자적으로 검증·저장하지 않으므로 이 초안만 적용하거나 회원 질문을 켜면 안 된다.
- `20260929_program_application_transition.sql` 초안은 전체 프로그램의 회원·비회원 신청에 같은 서버 상태 전이 함수를 사용한다. 프로그램 행 잠금으로 정원·대기를 판정하고, 신청 당시 질문·revision·답변을 함께 저장하며, 중복 신청을 멱등 처리한다. 전체 응답의 현행 상태 제약을 존중해 취소 시 행을 삭제하고 대기자를 같은 트랜잭션에서 승급한다. 별도의 빈 INSERT 전용 뷰가 RPC 스키마 캐시 누락 시 **같은 함수**로 들어가는 직접 테이블 대체 경로다. 챌린지·회차형 프로그램은 이 전체 신청 함수의 대상에서 제외한다.
- `20260929_program_application_direct_write_cutover.sql` 초안은 기존 광범위한 허용 정책에 제한 정책을 교차 적용해 일반 프로그램의 직접 신청 테이블 쓰기를 막는다. 관리자 출석 수정, 챌린지 기존 쓰기, 계정 병합 작업은 유지한다. **새 클라이언트 전환 전에 적용하면 구 클라이언트/열린 탭의 신청이 실패하므로 단독 적용 금지**다. 격리 DB에서 일반 프로그램 직접 쓰기 거부와 검증된 RPC/뷰 계속 작동을 확인했으나, 실제 동시 요청·운영 트리거 조합·구 클라이언트 전환 순서는 아직 검증 중이다.
- 정적 소비자 재검토 결과, `notice_responses`는 신청 외에도 챌린지 참여 자격, 커뮤니티 인원, 관리자 명단/출석, 사용자 여정, 방문 배지·프로그램 로그에 사용된다. 이들 중 다수는 `JOIN`을 명시적으로 검사하지만 일부는 출석 여부 또는 행 존재를 기준으로 한다. 회차 응답은 회차 출석과 `join_count` 갱신 트리거를 갖는다. 즉 전체/회차를 곧바로 하나의 물리 테이블로 합치는 것이 단순화는 아니다. **공통 질문 정의·검증과 단일 서버 쓰기 경계는 공유하고, 기존 두 응답 테이블은 각각의 운영 단위에 맞게 당분간 유지**하는 방향으로 목표를 조정한다. 물리 통합은 모든 소비자와 실데이터 대조에서 이점이 확인될 때만 별도 단계로 다룬다.

**다음 전환의 필수 조건:** 위 집계 결과를 반영한 전체·회차 × 회원·비회원의 서버측 답변 검증 및 원자적 정원/대기 처리, 관리자 출석·계정 병합·챌린지·구 클라이언트 호환 검증, 검토된 마이그레이션과 롤백 드라이런, 운영 스키마 변경에 대한 별도 명시적 승인. Firebase 배포는 별도 명시적 지시 전에는 진행하지 않는다.

### 프로그램 설정 화면 현황과 분리 기준

현재 `ProgramInfoSection.jsx`는 분리 전 약 1,795줄에 진행 일정·장소/모집·비회원 신청·포인트/피드백·호스트·챌린지·신청자 전용 기능을 함께 담았다. `WriteForm.jsx`에는 기본 콘텐츠, 저장 조정, 이미지, 게시 설정까지 있다. 복잡성의 핵심은 카드 수 자체보다 **신청 대상/질문, 일정/모집, 운영/사후 활동의 경계가 섞이고 각 카드의 활성화와 펼침이 하나의 상태처럼 보이는 것**이다. 회원 질문을 이 구조에 덧붙이면 중복 규칙이 늘어난다.

첫 무동작 변경으로 기존 비회원 신청 카드를 `src/features/programs/settings/GuestApplicationSettings.jsx`로 옮겼다. 기존 `guest_properties` 저장 형식·문구·필수 정보·질문 유형은 유지하고 사용되지 않던 로컬 열림 상태만 제거했다. 인증된 관리자 계정으로 로컬 `/admin`에 접속해 실제 프로그램 3개(RND PICNIC, 하이픈 스터디 클럽, HAIFN TABLE)의 편집 화면을 열었다. RND PICNIC의 기존 필수 질문 `성별` 표시, 비회원 신청 카드의 켜기/끄기, 임시 질문 추가·유형/선택지/필수 여부 변경·삭제를 확인했고, **저장 없이 취소한 뒤 다시 열어 원래 질문이 그대로인 것**을 확인했다. 첫 브라우저 점검에서 누락된 `Users` 아이콘 import로 편집 화면이 오류를 낸 것을 발견·수정하고, 누락 참조를 잡는 정적 검사를 추가했다. `editNoticeId`의 실제 숫자형과 PropTypes 불일치 경고도 수정했다. 이 수동 검사는 편집 화면 렌더링과 취소 경로에 한정되며 생성/수정 저장이나 회원 신청을 검증한 것은 아니다.

다음 무동작 분리로 `ProgramScheduleSettings.jsx`와 `LocationRecruitmentSettings.jsx`에 일정, 장소·모집 필드와 해당 지역 상태를 옮겼다. 장소 선택지는 한 상수 파일로 공유하고, 기존 필드 이름·값 변경 호출·조건부 표시·카드 순서는 유지했다. `ProgramInfoSection.jsx`는 약 1,795줄에서 1,299줄로 줄었지만 아직 운영/사후 활동 코드가 커서 완료된 구조로 보지 않는다. 정적 누락 참조 검사에 두 컴포넌트를 포함했고, 기준선 **16/16**과 빌드가 통과했다. 관리자 화면에서 단일 신청, 반복 회차 신청, 오픈 회차, 오프라인·온라인 챌린지의 일정 분기를 확인했다. 장소 `기타 → 하이픈` 전환과 기본 세부 공간 선택도 확인했고, 저장 없이 취소·재진입하여 원래 `2F SQUARE`가 유지됨을 확인했다. 새로고침 후 편집 화면을 다시 열었을 때 새 브라우저 오류는 없었다. 실제 저장·신청·동시성 테스트와 모든 프로그램 유형의 전수 비교는 별도 단계다.

호스트 카드와 진행자 조회·임시 복원 상태를 `HostSettings.jsx`로 옮겼다. 이 단계에서 부모는 약 1,072줄이 됐지만 아직 도메인별 분리가 더 필요하다. 분리 중 조회 효과를 처음에 부모에 남겨둔 누락을 코드 점검에서 발견해 곧바로 이동했고, 같은 누락을 앞으로 잡도록 검사를 JSX 이름뿐 아니라 JavaScript의 미정의 참조까지 확대했다. 관리자 화면의 기존 호스트 3명을 기준으로 활성화 꺼짐·켜짐에서 목록과 순서가 복원되고, 저장 없이 취소 후 재진입해도 원본이 유지됨을 확인했다. 외부 데이터 변경 없이 화면과 상태 소유권만 옮긴 단계다.

보상·피드백 카드를 `RewardFeedbackSettings.jsx`로 분리했다. 항상 `false`였던 과거 질문 편집 블록은 실행 경로가 없어서 제거했고, 실제 연결 설문은 기존 `ProgramSurveyPicker`를 그대로 사용한다. 부모는 약 820줄이 됐다. 관리자에서 기존 포인트와 연결 설문 표시, 카드 끄기·켜기 후 설문 재표시, 저장 없이 취소·재진입 후 원본 보존을 확인했다. 이 확인은 화면 편집 경로에 한정되며 설문 제출이나 포인트 지급을 새로 실행한 것은 아니다.

챌린지 미션·커뮤니티 설정과 해당 커뮤니티 조회 상태를 `ChallengeSettings.jsx`로 옮겼다. 관리자 신규 작성 화면에서 오프라인 미션 추가, 온라인 전환, 커뮤니티 선택 영역을 확인하고 저장 없이 취소했다. 이어 신청자 전용 버튼·팝업·팀 배치·랜덤 질문 설정을 `ApplicantExperienceSettings.jsx`로 분리했다. 기존 RND PICNIC 편집 화면에서 카드 활성화와 노출 기준의 시작→종료 전환이 반영됨을 확인한 뒤 저장 없이 취소했다. 이 변경은 저장 형식이나 업무 규칙을 바꾸지 않으며, 분리된 모든 설정 컴포넌트를 미정의 참조 검사에 포함했다. `npm run test:baseline` 16/16이 통과했다. 실제 저장 및 학생 노출은 아직 검증하지 않았다.

상단 프로그램 대상·지역 선택과 운영 방식/반복·회차 신청 선택을 각각 `ProgramAudienceSettings.jsx`, `ProgramParticipationSettings.jsx`로 옮겼다. `ProgramInfoSection.jsx`는 약 1,795줄의 혼합형 컴포넌트에서 36줄의 조합 컴포넌트가 됐다. 기존 프로그램 편집 화면에서 단회→반복→회차별 신청 전환 시 신청 방법과 회차 안내 항목이 노출됨을 확인하고 저장 없이 취소했다. **화면 코드의 분리는 완료됐지만** 설정 화면의 정보 구조 재배치, 저장/검증 소유권 분리, 회원 추가 질문, 학생·공개 신청과 실제 저장 회귀 검증은 별도 단계다. 줄 수 감소만으로 전체 리팩토링 완료를 의미하지 않는다.

화면 재배치는 기존 색·브랜드·필드명·저장 형식을 바꾸지 않고, `기본 정보 → 프로그램 구분 → 일정과 모집 → 신청 정보 → 진행 설정 → 종료 후 → 게시/이미지`로 정보 관계를 드러내는 작업이다. 우선 모든 필드를 유지한 채 그룹과 목차만 배치한다. 섹션별 저장 소유권과 오류 이동은 실제 저장 경계가 확인된 다음 별도로 다룬다. 이 화면은 관리자용 복합 폼이므로 홍보 페이지용 시각 효과나 새 디자인 시스템을 도입하지 않는다.

정보 구조의 첫 재배치에서는 기존 산세리프 서체와 색(`흰색 #ffffff`, `배경 #f8fafc`, `경계 #e2e8f0`, `본문 #1e293b`, `강조 #2563eb`)을 유지했다. 더 많은 카드 장식은 추가하지 않고, 프로그램 설정 안에 다섯 개의 의미 그룹과 목차를 둔다. 넓은 화면의 목차는 왼쪽에, 좁은 화면에서는 가로로 배치한다. 모든 필드는 계속 화면에 존재하므로 탭 뒤에 숨은 오류가 생기지 않는다.

```text
기본 콘텐츠(기존 위치)
프로그램 설정  [구분 | 일정·모집 | 신청 정보 | 진행 설정 | 종료 후]
              └─ 선택한 그룹으로 스크롤, 필드는 항상 표시
게시·이미지(기존 위치)
```

`ProgramSettingsLayout.jsx`와 `ProgramInfoSection.jsx`에서 이 배치를 로컬로 적용했다. 관리자 RND PICNIC 편집 화면에서 목차의 `신청 정보`와 `종료 후` 이동, 기존 게스트 질문과 연결 설문 표시를 확인하고 저장 없이 취소했다. 16/16 기준선은 통과했다. 실제 저장, 전체 프로그램 유형의 시각 비교, 모바일 화면과 데이터 제출은 아직 확인하지 않았다.

**회원 질문 구현의 안전 중단 지점:** 현재 회원의 전체 프로그램 신청은 `useNotices.js`에서 클라이언트가 정원을 조회하고 `noticesApi.upsertStudentResponse()`로 직접 응답 테이블을 쓰며, 취소 후 대기자 승급도 별도 요청이다. 회차 신청은 `programSessionsApi.respond()`가 답변 인자를 받지 않는다. 두 경로 모두 기존 `application_answers` 열만으로는 신청 당시의 질문 정의·대상·필수 여부를 보존하거나 서버에서 확인할 수 없다. 따라서 관리자 화면에 회원 질문만 먼저 추가하면 답변 누락 또는 정원·대기 불일치를 만들 수 있다. 회원 질문은 검토된 버전/답변 스키마와 전체·회차 신청의 원자적 쓰기 경계를 마련하고, 격리 드라이런과 명시적 승인 후에 연결해야 한다. 운영 DB·배포는 변경하지 않았다.

### 첫 코드 분리: 기존 비회원 신청 질문 호환 계층

`src/features/programs/applicationFields.js`에 기존 `guest_properties.custom_fields` 읽기·공개 항목 필터·저장 직렬화·필수 답변 판정을 모았다. 관리자 편집/저장, 공개 신청, 명단 표시의 기존 호출을 이 계층으로 연결했다. 데이터 형식, 질문 대상, UI 배치, DB 쓰기 경로는 바꾸지 않았다. `scripts/test-legacy-application-fields.mjs`가 과거 필드 ID, 빈 항목, 유형 기본값, 선택지, 필수 답변 동작을 확인한다. 14개 회귀 검사와 `npm run build`가 통과했다. 이 계층은 과거 게스트 설정의 호환 경계이며, 새 회원 질문 버전 구조가 확정되면 둘을 무리하게 같은 JSON 키로 합치지 않는다.

## 목표 구조와 경계

기능별로 코드를 모으되 한 번에 전체 디렉터리를 이동하지 않는다. 기존 import 경로를 사용하는 코드는 기능 단위 전환이 끝날 때까지 유지한다.

```text
src/
  app/                 라우팅, 인증 게이트, 관리자/학생 화면 껍데기
  features/
    programs/          설정, 신청, 회차, 참여자, 출석
    visits/            입퇴실, 키오스크, 방문 기록
    surveys/           질문 정의, 응답, 결과
    community/         채널, 게시물, 참여 자격
    accounts/          회원 프로필과 계정 작업
    notifications/     발송 요청과 결과
  shared/              실제로 둘 이상 기능에서 쓰는 UI·날짜·오류 처리
```

각 기능 안의 책임은 다음과 같이 구분한다.

| 계층 | 책임 | 금지할 결합 |
| --- | --- | --- |
| 화면 컴포넌트 | 표시, 접근성, 입력, 사용자 피드백 | 직접 DB 저장, 정원·권한 계산 |
| 화면 훅 | 조회 시점, 로딩·오류·선택 상태 | 서로 다른 기능의 업무 규칙 복제 |
| 도메인 모델 | 신청 가능 여부, 질문 검증, 날짜·상태 변환 | React·브라우저 저장소 의존 |
| 데이터 접근 | 테이블·RPC·직접 테이블 대체 경로, 결과 정규화 | 화면 문구·모달 상태 |
| DB | 권한, 제약, 원자적 상태 변경, 원본 보존 | 클라이언트 상태에 대한 신뢰 |

작은 컴포넌트의 기준은 독립적으로 설명·검증 가능한 사용자 작업이다. 단순한 라벨이나 입력칸마다 파일을 만들지 않는다. 한 화면에서만 쓰는 상태는 그 화면 가까이에 두고, 여러 경로가 공유하는 규칙만 기능 계층으로 올린다.

## DB 데이터 소유권과 목표 구조

DB 변경을 허용하되, 모든 영역을 하나의 범용 테이블이나 JSON 문서로 합치지 않는다. **업무 상태를 변경하는 경로는 데이터마다 하나로 정하고**, 다른 기능은 그 기록을 참조한다. 현재 마이그레이션 파일은 운영 DB의 실제 상태를 보증하지 않으므로 변경 전에는 운영 스키마·권한·데이터 분포를 읽기 전용으로 대조한다.

| 영역 | 소유하는 데이터와 경계 | 설계 원칙 |
| --- | --- | --- |
| 계정·권한 | 사용자 신원, 역할, 회원/게스트 구분, 동의 이력 | 신청 답변이나 출석 상태를 사용자 프로필에 넣지 않는다. 기존 `account_security` 경계를 존중한다. |
| 콘텐츠·프로그램 | 공지/게시 콘텐츠와 프로그램 설정, 회차 | `notices`의 공통 콘텐츠와 프로그램 고유의 모집·신청 규칙을 구분한다. 자주 검사하는 규칙은 제약 가능한 컬럼으로, 유연한 표시 정보만 JSON으로 둔다. |
| 신청 | 프로그램 전체/회차 신청, 참여·대기·취소 상태, 신청 당시 질문 버전과 답변 | 한 신청의 상태를 한 기록에서 판정한다. 회차는 반드시 해당 프로그램 소속이어야 하며 동일 대상 중복 신청은 DB가 막는다. |
| 출석·방문 | 프로그램 참여 출석과 센터 입퇴실 로그 | 출석과 방문은 서로 다른 사실로 보존한다. 출석 여부를 신청 상태와 혼동하지 않고 원본 로그를 덮어쓰지 않는다. |
| 설문 | 설문 양식·불변 버전·제출·집계 | 신청 질문과 편집/검증 도구는 공유할 수 있으나 설문 제출과 신청 기록의 수명주기는 분리한다. |
| 커뮤니티·보상·알림 | 게시물/참여 자격, 포인트 원장, 발송 요청/결과 | 신청·출석 원본을 참조해 자격과 보상을 계산하고 별도 기록을 유지한다. 파생 결과가 신청의 원본이 되지 않는다. |

프로그램 영역의 현재 우선 목표는 다음과 같다. 이는 **검증할 설계안**이며 기존 소비자·권한·실데이터 조사 결과에 따라 세부 열을 확정한다. 다른 운영 단위의 신청을 물리적으로 합치는 작업은 기본 전제에서 제외한다.

```text
notices (현재 콘텐츠·프로그램 설정의 기록원)
  ├─ application_form + revision (현재 질문 정의, MEMBER/GUEST/ALL 대상)
  ├─ notice_responses (전체 프로그램·기존 챌린지 신청, 신청 당시 질문 스냅샷)
  └─ daily_program_sessions (회차)
       └─ daily_program_session_responses (회차별 신청·출석, 신청 당시 질문 스냅샷)
open_program_attendance (신청 없는 열린 프로그램의 출석)
```

- 회원·비회원은 **하나의 신청 질문 편집기와 검증 규칙**을 사용하되, 질문의 대상은 명시적으로 저장한다. 이름·연락처 같은 신원 정보와 개인정보 동의는 임의 추가 질문과 구분한다. 별도 버전 테이블을 선행 도입하는 대신, 현재 정의의 revision과 **각 신청 당시의 불변 질문 스냅샷·답변**을 저장한다. 이 방식이면 질문 수정 시 과거 신청을 정확히 표시할 수 있고 공지 저장과 질문 변경도 한 행의 트랜잭션으로 묶을 수 있다. 정의 편집 이력 전체가 별도 요구될 때만 버전 테이블을 추가한다.
- 가변 질문 답변은 불변 질문 정의와 연결된 JSON으로 저장할 수 있다. 모든 질문을 별도 열로 만들거나, 조회 요구가 없는 답변마다 행을 분해하지 않는다. 질문 ID·유형·필수 여부·선택지·답변 크기는 서버/DB에서도 검사한다.
- 신청 없이 참여하는 열린 프로그램도 있으므로 출석은 신청의 하위 기록으로 강제하지 않는다. 신청이 있는 경우에만 관계를 연결하고, 출석의 실제 기준(회차/일자/프로그램)은 현행 사용처를 대조해 정한다.
- 전체 신청의 `(notice_id, user_id)`와 회차 신청의 `(session_id, user_id)`를 각각 유일하게 보장한다. 회차의 프로그램 일치, 정원·대기 순서·취소 후 승급, 본인 확인, 중복/동시 요청은 각 운영 단위의 서버 트랜잭션 경계에서 보장한다. RPC가 없어 직접 테이블 경로를 쓰는 경우에도 **동일한 DB 보호**를 통과해야 하며, 클라이언트의 정원 계산만으로 처리하지 않는다.
- `notice_responses`는 챌린지·커뮤니티·설문 자격 등에서도 읽는다. `daily_program_session_responses`는 회차 명단·출석에서도 읽는다. 하나의 질문 모델과 신청 API를 공유하더라도 두 물리 테이블은 각각 하나의 운영 단위에 대해 단일 기록원으로 유지할 수 있다. 챌린지 분리는 별도 소비자 검증 후 판단한다.

DB 전환은 `확장(새 스키마·제약·권한) → 복사/검증(원본 보존, 상태·답변·소유자 대조) → 병행 읽기 비교 → 쓰기 전환(호환 경로와 되돌림 준비) → 안정화 후 구 경로 정리`로 나눈다. 오랜 기간 두 테이블에 독립적으로 쓰는 이중 기록은 피한다. 운영 적용 전에 중복·누락·고아 FK, 권한별 접근, 신청 동시성, 기존 통계/포인트/커뮤니티 결과와 쿼리 비용을 확인한다. 원본 테이블과 로그의 삭제는 이 계획에 포함하지 않는다.

## 단계별 작업

### 0. 기준선과 영향 지도

1. 관리자·학생·비회원·공개 페이지의 주요 작업 목록과 데스크톱/모바일 화면을 기록한다.
2. 신청, 출석, 포인트, 커뮤니티 자격, 설문 자격, 알림, 사용자 여정의 테이블·RPC·직접 대체 경로를 읽기/쓰기별로 목록화한다.
3. 정상, 빈 상태, 오류, 로그인 만료, 정원 마감, 대기, 취소, 재신청의 현재 동작을 적는다.
4. 기존 테스트를 기능별 명령으로 묶고, 현재 검증하지 못하는 경로를 표시한다.

통과 조건: 변경 대상 기능의 호출자와 소비자가 누락 없이 나열되고, 전후 비교 기준이 있다.

### 1. 화면 껍데기와 기능 경계 정리

1. 관리자/학생 대시보드의 메뉴 선택과 화면 렌더링을 작은 화면 껍데기로 분리한다.
2. 각 메뉴의 조회는 해당 화면이 필요할 때 시작하도록 정리한다. 기존 실시간 구독과 인증 상태 유지 조건을 먼저 기록한다.
3. 화면별 지연 로딩을 적용할 때 첫 진입, 탭 전환, 복귀, 알림 링크 이동을 함께 확인한다.

통과 조건: 메뉴·URL·뒤로가기·로그인 복구·실시간 갱신과 화면 구성이 동일하다. 불필요한 화면 데이터 조회가 줄어든다.

### 2. 프로그램 설정 화면의 구조 분리

첫 변경은 표시 구조와 상태 소유권만 다룬다. 저장 데이터 형식과 업무 규칙은 바꾸지 않는다.

```text
ProgramEditor
  BasicInformation
  ProgramSchedule
  RecruitmentSettings
  ApplicationSettings
  HostSettings
  ChallengeSettings
  PostProgramSettings
  PublishingSettings
```

- `ProgramEditor`는 폼 수명주기와 저장을 조정한다. 섹션은 해당 필드와 오류를 담당한다.
- 모집/회차/챌린지의 표시 조건과 저장 조건을 공통 모델 함수로 옮긴다.
- 활성화 스위치와 상세 펼침을 분리한다. 접힌 섹션의 오류는 자동으로 표시·이동한다.
- 화면 재배치는 구조 분리 전후 동작이 동일함을 확인한 다음 별도 변경으로 수행한다.

통과 조건: 기존 프로그램을 수정 없이 열고 저장해도 의미 있는 데이터 변경이 없고, 각 프로그램 유형의 입력·검증·저장이 동일하게 작동한다.

### 3. 프로그램 신청 도메인 정리와 회원 질문 추가

1. 설문의 기존 질문 편집/검증 도구를 신청서에 재사용할 수 있는 범위를 검토한다. 신청용 불변 버전과 제출 기록은 설문 응답에서 분리한다.
2. 회원/비회원의 추가 질문을 한 편집기에서 정의하고 질문별 대상을 지정한다. 기존 게스트 질문은 원래 대상과 답변을 보존한다.
3. 관리자, 학생, 공개 페이지가 동일한 신청 규칙과 화면을 사용한다. 질문이 없는 회원의 현재 신청 경험을 유지한다.
4. 전체/회차 신청의 소비자와 각각의 기록원 경계를 확정한다. 출석·포인트·대기·커뮤니티 권한의 기준을 공통 도메인 API로 명시하되, 물리 테이블 통합은 실익과 안전성을 입증할 때만 별도 전환한다. 챌린지 신청 등 의미가 다른 기록은 무리하게 합치지 않는다.
5. 신청·취소·대기자 승급의 동시성, 본인 확인, 중복 요청, 질문 변경 중 제출을 DB에서 검증한다. 모든 RPC에는 프로젝트 규칙에 맞는 직접 테이블 대체 경로와 동등한 DB 보호 장치를 설계한다.

통과 조건: 일반/회차 × 회원/비회원 × 참여/대기/취소/재신청의 결과가 화면, DB, 관리자 명단에서 일치한다. 기존 신청·출석·답변 기록의 건수와 소유권이 보존된다.

### 4. 나머지 큰 기능을 같은 방식으로 정리

프로그램 작업의 검증 방식이 안정되면 방문·키오스크, 회원·인증, 설문, 커뮤니티·알림, 관리자 통계 순으로 적용한다. 각 기능은 하나의 작업 묶음으로 분리하며 다른 기능의 DB 구조를 동시에 바꾸지 않는다. 이미 분리된 코드와 검증된 서버 계층은 재사용한다.

통과 조건: 수정한 화면에서 직접 DB 접근과 중복 업무 규칙이 줄고, 기존 권한·원본 기록·실시간 동작이 유지된다.

### 5. 정리와 지속 검증

- 더 이상 참조하지 않는 파일·호환 경로는 실제 참조와 복구 가능성을 확인한 후에만 정리한다.
- 기능별 핵심 테스트를 한 명령과 CI 검증에 연결한다. 실제 DB에 접근하는 검사는 격리 검사와 분리한다.
- 큰 번들 경고를 기능별 지연 로딩으로 개선하고 초기 진입·탭 전환 성능을 비교한다.
- 구조 원칙과 데이터 소유권을 짧은 개발 문서로 유지한다.

## 단계마다 수행할 검증

| 구분 | 사전·사후 확인 |
| --- | --- |
| 정적 검사 | import 경로, 사용하지 않는 파일, 직접 DB 접근, RPC 대체 경로, 순환 의존 |
| 기능 모델 | 모집 시간, 프로그램 종류, 회차, 필수 질문, 중복·취소·대기 상태 |
| 격리 DB | 권한 거부, 동시 신청, 대기자 승급, 기존 데이터 복사·대조, 원본 보존 |
| DB 이전 | 전체/회차·회원/게스트별 건수와 상태, 답변·출석·소유권 대조, 중복·고아 FK, RLS 권한표, 주요 조회 계획 |
| 브라우저 | `npm run dev`의 `http://localhost:5173`에서 관리자·학생·게스트·공개 화면, 데스크톱·모바일, 오류·빈 상태·키보드 조작 |
| 통합 | 신청→명단→출석→포인트·설문·커뮤니티 자격·알림의 연결 |
| 빌드 | `npm run build`, 변경 전후 큰 청크와 로딩 상태 비교 |

한 단계가 실패하면 다음 기능으로 넘어가지 않고 해당 단계의 변경만 되돌릴 수 있도록 작업 단위를 유지한다. 테스트가 통과해도 화면 차이와 DB 결과 차이를 별도로 확인한다.

## 운영 변경 경계

- 로컬 구조 분리와 화면 검증은 `npm run dev` 기준으로 진행한다.
- 운영 스키마는 검토된 마이그레이션, 명시적 승인, 드라이런 또는 동등한 영향 점검 후에만 변경한다.
- 운영 데이터와 원본 로그는 삭제·리셋하지 않는다. 이전 시 원본과 새 기록을 건수·상태·소유권별로 대조하고 복구 경로를 준비한다.
- Firebase Hosting 배포는 별도의 명시적 지시가 있을 때만 수행한다.
